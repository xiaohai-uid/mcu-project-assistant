# MCU Project Assistant — 首个可付费参考套件规格

## Problem Statement

独立硬件和物联网开发者通常能找到一段示例代码，却很难确认这段代码是否适合自己手里的具体板子和器件：芯片、模组、整板和电商商品经常被混为一谈，参数没有条件和来源，接线冲突不会在早期暴露，编译成功也常被误解成真实硬件已经成功运行。

当前项目已经具备本地项目、ArtifactVersion、Proposal、接线检查、固件生成、BuildRecord、ValidationRecord、真实设备识别、上传和串口能力；知识目录的静态参数混用与缺源问题已在首发矩阵路径上修复（b0ff6c2：候选平台必须携带官方来源与事实，RP2040 已移出候选矩阵），真实硬件验收仍待实物完成。

首个商业版本需要把这些能力连成一条可信的本地工作流，并且只支持一个明确的 Reference Kit：Espressif `ESP32-S3-DevKitC-1-N8R8`，集成 `ESP32-S3-WROOM-1-N8R8`，优先按 v1.1 板级引脚图支持。

## Solution

把现有的推荐、接线、编译、设备和证据能力接在同一个应用边界上，形成如下用户结果：

`项目输入 → 精确板卡/器件身份 → 有来源的参数 → 接线约束 → 固件 → 真实编译 → 可选仿真 → 实物上传/串口观察 → 可复查报告与 BOM`

系统只对实际发生且保存了证据的事情给出通过状态。所有硬件事实必须绑定精确身份、对象层级、来源、版本、时间、条件和可信度；未知值保持未知，不用经验值填空。

首个付费承诺是：独立开发者可以在本地把一个 MCU 项目推进到可编译、接线约束清楚、证据状态透明，并在有真实 Reference Kit 时完成上传和启动输出验收。学生使用同一核心的免费或低价入口，小型团队以后复用同一核心，不建设三套引擎。

## User Stories

1. 作为独立硬件开发者，我想输入我的项目目标和已有器件，以便得到一条可执行的开发路径。
2. 作为独立硬件开发者，我想明确看到系统支持的是哪一块具体开发板，以便避免把芯片资料误当成整板资料。
3. 作为用户，我想看到开发板的品牌、型号、模组、Flash、PSRAM、USB、供电和板级版本，以便判断手里的实物是否匹配。
4. 作为用户，我想看到每一个关键参数的官方来源、文档版本和查询日期，以便在不相信系统时自己复查。
5. 作为用户，我想看到参数的测试条件和性质，例如建议值、最大值、典型值或峰值，以便不把不同含义的数字混在一起。
6. 作为用户，我想看到未知或没有可靠来源的参数被明确标记，以便知道哪些地方仍需要人工确认。
7. 作为用户，我想让芯片、模组、开发板和具体商品分别保存，以便同一芯片不同开发板不会共用错误的引脚或存储信息。
8. 作为用户，我想选择精确的外设型号或商品身份，以便系统不会把“继电器模块”“OLED”这类模糊名称直接当成可生产器件。
9. 作为用户，我想看到供电、电平、占用引脚、总线复用和启动相关引脚的限制，以便在烧坏板子之前发现明显接线风险。
10. 作为用户，我想先查看系统建议并确认，再生成或修改固件，以便 AI 不会绕过我的决定直接改变正式 ArtifactVersion。
11. 作为用户，我想让系统对接线约束进行检查，并看到每条警告对应的板卡或器件资料，以便理解为什么不能这样接。
12. 作为用户，我想用固定版本的 Arduino-ESP32 工具链真实编译，以便同一份项目在之后能够尽量复现。
13. 作为用户，我想看到完整的构建参数、工具链版本、输入版本、输出文件和哈希，以便判断编译结果是否属于当前项目。
14. 作为用户，我想知道系统只是发现了一个端口，还是确实把固件上传到了真实开发板，以便不把端口发现误认为烧录成功。
15. 作为用户，我想在真实开发板上看到预期的串口启动输出，以便完成第一步实物验收。
16. 作为用户，我想把仿真结果与实物结果分开看，以便仿真通过不会掩盖 USB、供电、电流和真实负载仍未验证的事实。
17. 作为用户，我想看到 `local-ready`、`simulation-ready` 和 `physical-accepted` 的区别，以便知道当前结果能否交付给别人。
18. 作为用户，我想在缺少工具、凭据或真实硬件时看到“未运行/待验证/阻塞”，以便系统不会给出虚假的绿色通过。
19. 作为用户，我想把器件的价格、库存和数量档位作为带日期的采购观察，以便估算成本和决定去哪里购买。
20. 作为用户，我想看到价格对应的精确供应商编号、人民币单价、数量、费用、库存状态、来源链接和查询时间，以便价格不会脱离上下文。
21. 作为用户，我想让价格只影响采购建议，不影响兼容性和安全判断，以便低价替代品不会自动替换原器件。
22. 作为用户，我想从项目输入得到一份可导出的 BOM，以便自行采购；我不需要系统替我支付或下单。
23. 作为用户，我想区分系统生成的 BOM 和我原本输入的 BOM，以便知道哪些物料是我的决定、哪些是系统建议。
24. 作为用户，我想在资料更新后看到旧版本仍然保留，以便旧项目不会被新资料静默改写。
25. 作为用户，我想看到每条推荐引用了哪些事实、仍缺哪些事实，以便知道系统的结论是否值得信任。
26. 作为学生用户，我想用较低成本体验同一条流程，以便学习真实的工程习惯，而不是使用一个被拆开的简化引擎。
27. 作为未来的小型硬件团队，我想复用个人版的项目、证据和 BOM 语义，以便以后扩展协作时不需要推倒重来。
28. 作为维护者，我想只维护一个本地优先核心，以便不用同时维护学生版、个人开发者版和团队版三套逻辑。
29. 作为维护者，我想用自动化测试验证用户能从输入走到结果，以便每次更新不会只修好单个模块却破坏整条路径。
30. 作为维护者，我想把真实硬件验收作为明确的外部条件，以便没有板子时测试仍可运行，但发布不会错误地宣称已完成。

## Implementation Decisions

- **产品边界**：首发是本地优先的 MCU 工程助手，不是完整 EDA、商城、制造平台或 SaaS。首发 Reference Kit 只有 `ESP32-S3-DevKitC-1-N8R8` / `ESP32-S3-WROOM-1-N8R8`，其他平台不能以未经核验的静态事实参与首发推荐或商业就绪判断。
- **工具链**：Arduino-ESP32 核心首版固定为 `3.3.11`；基础 FQBN 为 `esp32:esp32:esp32s3`，8 MB Flash、OPI PSRAM 和其他构建选项必须显式保存为完整解析结果。Arduino CLI 版本单独保存，不把 CLI 版本和核心版本混成一个字段。
- **板级版本**：优先支持 ESP32-S3-DevKitC-1 v1.1 引脚图。首版验收必须记录实物版本；官方资料指出初始版本和 v1.1 仍同时存在，RGB LED 引脚不同。
- **知识身份**：Platform 和 ComponentDefinition 必须区分芯片、模组、开发板、模块、裸器件和工具。记录品牌、制造商料号、供应商 SKU、变体、对象层级、生命周期和关联对象。
- **知识事实**：每个事实包含字段名、数值、单位、工作条件、参数性质、来源 URL、来源对象、文档标题、文档版本/修订、发布日期或修改日期、查询时间、时效状态、可信度和被替代关系。没有条件的数值不作为完整事实。
- **可信度**：至少支持 `official-direct`、`official-index`、`measured`、`user-supplied`、`inferred`、`unsupported`。推断和无来源数据必须显式显示，不能支持商业就绪通过。
- **推荐追踪**：推荐结果保存触发它的事实、约束和缺失资料。替代型号必须是候选，只有用户确认且候选资料满足约束后才进入正式 BOM。
- **价格观察**：首版以立创商城公开、可人工核查的信息为主要中国市场来源。每条 PriceObservation 绑定精确供应商 SKU 和制造商料号，分开保存数量档（优先 1、10、100）、CNY 单价与总价、库存状态、运费、税费、来源链接和查询时间。价格/库存只做采购建议和成本估算，不证明兼容性、安全、编译或实物验收。
- **BOM**：BOM 是可复查结果，保存用户输入与系统建议的区分、数量、精确身份、候选替代、资料状态和价格观察。首版只要求 CSV/Markdown 导出，不接支付、账号或自动下单。
- **证据语义**：保留 ArtifactVersion、BuildRecord、ValidationRecord、DebugEvidence 的现有分离。编译、接线检查、仿真、真实上传、串口观察分别保存，不能共用一个 `hardwarePassed` 布尔值。
- **就绪状态**：`local-ready` 要求精确身份和来源记录、接线约束通过、固定工具链真实编译、构建产物哈希和完整结果保存；`simulation-ready` 在此基础上增加独立仿真证据，但不能替代实物；`physical-accepted` 在此基础上要求记录实物版本、真实 USB 识别、上传成功、上传校验成功和预期串口启动输出；首个 Reference Kit 的 `paid-release-ready` 必须同时具备 `local-ready` 和 `physical-accepted`。
- **缺失证据**：没有工具、凭据、仿真访问权限或实物时只能是 `not-run`、`unavailable`、`blocked` 或 `pending`，不能成为 `pass`。
- **应用边界**：通过现有 application capability 和 HTTP API 作为唯一产品接缝。推荐、接线、构建、设备检测、上传和串口仍由现有能力承载；新增资料、价格和就绪结果接入同一边界，不建立第二套流程。
- **持久化**：SQLite 保存身份、版本、状态、来源引用、摘要和诊断；固件、编译输出、原始日志和设备证据继续保存为 workspace 文件并以引用关联，避免数据库膨胀。
- **执行模式**：v1 维持 `local` 单进程、SQLite 和本地文件；云端、团队协作和托管队列是后续适配器，不改变本地证据语义。
- **历史处理**：不为错误的静态字段建立兼容层。旧的宽泛目录记录需要被修正、标记为未核验或移除出首发推荐路径；不允许旧字段继续制造“已支持”的假象。

## Testing Decisions

- 测试用户可观察的结果、状态和证据，不测试内部实现细节。每个测试都应回答“用户现在看到了什么、系统保存了什么、缺失时是否明确阻塞”。
- 纯规则测试覆盖：精确身份校验、来源和时效校验、数值条件/性质校验、芯片/模组/开发板分层、价格观察不可比条件、替代型号不自动替换、就绪状态推导和缺证据阻塞。
- 知识目录测试覆盖：ESP32-S3-DevKitC-1-N8R8 v1.1 的板级引脚、USB、UART、I2C、SPI、strapping、Flash/PSRAM 和 LED 事实；组件测试覆盖精确料号缺失、官方资料缺失和第三方模块不可推断的情况。
- 持久化测试覆盖：身份和来源版本保存、旧观察保留、PriceObservation 字段分离、BOM 与价格观察关联、BuildRecord/ValidationRecord/DebugEvidence 引用不串线、无证据的历史记录不会变成 ready。
- HTTP/application 集成测试覆盖：用户通过现有能力完成推荐、接线检查、构建、设备检测、上传和串口读取；每一步返回与数据库/工作区证据一致的结果。
- 端到端黄金路径覆盖：创建 Project → 选择精确 Reference Kit → 选择器件 → 生成/确认 Proposal → 接线检查 → 生成固件 → 构建 → 查看来源和证据 → 导出 BOM → 在有夹具时检测/上传/串口验收。
- 失败路径覆盖：工具链缺失、来源过期、板卡版本不匹配、strapping 引脚冲突、构建失败、上传超时、设备变化、串口断开、仿真不可用、价格库存未知；所有失败都必须保持为失败或待验证。
- 真实硬件验收不伪造：CI 使用确定性 DevicePort/CompilerPort 夹具测试状态机，真实板卡验收另留人工或现场记录，必须绑定板卡版本、固件哈希、接线版本、操作者和日期。
- 参考现有测试先复用其最高层入口：MCU 推荐黄金路径、接线约束测试、BuildRecord 持久化测试、真实设备上传/串口端到端测试和生产运行时缺工具 fail-closed 测试。

## Out of Scope

- 首发不做监管证书、EMC/CE/FCC 证明、企业采购资质或完整商业合规材料。
- 首发不做 Arduino UNO、RP2040、STM32 等其他平台的完整并行支持；它们若没有经过来源核对，不能继续以完整支持身份出现。
- 不做百万级器件库、完整 PCB 绘图、PCB 制造、SMT 贴片、Gerber 生产预览或企业级 ERP。
- 不做商城账号、支付、自动下单、订单履约和库存实时承诺。
- 不把淘宝、京东、分销商、批发报价与立创商城价格混成同一价格模型。
- 不把 Wokwi 或其他仿真当作真实电压、电流、USB、热、EMI、负载或装配验证。
- 不做多用户 SaaS、云端队列、团队权限、云同步和托管硬件执行。
- 不为错误的旧静态字段建立长期兼容迁移层。
